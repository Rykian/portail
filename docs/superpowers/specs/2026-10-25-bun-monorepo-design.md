# Full-Bun monorepo — design

Date: 2026-10-25

## Intent

The repo runs two toolchains side by side: the Next.js portal at the root on npm + Node 24, and `updater/` on Bun 1.4.4 with its own lockfile and CI job. `shared/updater-api.ts` is used by both but is not a package: each side reaches it through ad-hoc `paths` aliases, the updater forces `zod` resolution to its own `node_modules`, and its Dockerfile symlinks `/app/node_modules` so `shared/` can find `zod`.

Goal: one toolchain (Bun) and one workspace layout. This is a simplification, not a feature.

## Goals

- Bun is the only package manager: one root `bun.lock`, no `package-lock.json`, no `updater/bun.lock`.
- Bun is the only runtime, including the portal in production: the `ghcr.io/rykian/portail` image runs on `oven/bun`, not `node`.
- Bun workspaces, layout:

  ```
  apps/portail/      everything Next today: app, components, lib, e2e, scripts, types, auth.ts, proxy.ts (+ test),
                     next/playwright/vitest/tsconfig/components.json configs, services.example.yml, .env.development,
                     data/ (gitignored), Dockerfile
  apps/updater/      today's updater/, with its Dockerfile
  packages/shared/   today's shared/ (updater-api.ts + test), package "@portail/shared", zod as its own dependency
  package.json       workspaces + root scripts
  bun.lock
  .oxlintrc.json, .oxfmtrc.json, .github/, deploy/, docs/, README.md, AGENTS.md stay at the root
  ```

- Root scripts run across all workspaces: `lint` (oxlint), `format` / `format:check` (oxfmt), `typecheck`, `test`. `e2e` runs the portal's Playwright suite.
- CI uses only `oven-sh/setup-bun` (Bun pinned to 1.4.4). No `setup-node`.
- Every import of the shared contract becomes `@portail/shared/updater-api` (portal used `@/shared/...`, updater `@shared/...`). The `@shared` alias, the forced `zod` path in the updater's tsconfig and vitest config, and the `/app/node_modules` symlink go away.

## Non-goals

- No product or behaviour change. Application code changes only where an import path or a `node` invocation must change.
- No dependency upgrades beyond what the switch forces.
- No monorepo task runner (Turborepo, Nx…). Bun workspaces + `bun run --filter` are enough.
- No change to how production is deployed: `deploy/*.yml`, container paths (`/data`, `/app`), ports (3000, 8080) and image names stay as they are.

## Anti-goals

- The portal image "works" but a feature silently breaks under Bun (auth, `proxy.ts`, icon fetching, updates page streaming). Guards: the e2e suite under `bun --bun next dev`, plus the production smoke test (see Verification); the rest is checked once deployed.
- `git mv` lost: files must be moved, not deleted and re-created, so history follows.
- A step that leaves CI red on `main`.

## Constraints and known risks

- **Standalone `server.js` under Bun is not documented.** Next 16.4.3's docs list Bun as a verified deployment adapter and Bun's guide documents `bun --bun next build/start`, but neither mentions `output: "standalone"`. Step 1 (below) settles this before anything else moves.
- **Bun version drift has broken Next builds** (reported on Next 16.3 between Bun 1.3.12 and 1.3.14). Pin Bun to 1.4.4 everywhere: root `packageManager`, CI, both Dockerfiles.
- **Playwright's test runner is built for Node.** The server under test must run on Bun; if the runner itself cannot run under Bun, `bunx playwright test` falling back to Node in CI is tolerated (it is a dev tool, not shipped). `npx playwright install --with-deps` becomes `bunx playwright install --with-deps chromium`.
- `scripts/fetch-icons.mjs` runs inside the portal image (`outputFileTracingIncludes` keeps `yaml` for it); it must run with `bun` there. README's `node scripts/fetch-icons.mjs` usage changes accordingly.
- Portal tests run with `bun --bun vitest run`, as the updater already does.
- `AGENTS.md` is regenerated by `next dev` next to the Next app; once the app moves, decide whether the root copy stays (builder's call, see below).

## Plan shape (decided)

Each step is independently reviewable and passes the checks listed under Verification.

1. **Spike — standalone under Bun (throwaway).** On the current layout: `bun --bun next build`, then `bun .next/standalone/server.js` (with `.next/static` copied next to it, as the Dockerfile does), then run the production smoke test below. Also run `fetch-icons.mjs` with Bun from the standalone output. If this fails and can't be fixed cheaply, stop and come back: the "no Node in production" goal is re-discussed before going further.
2. **npm → Bun, same layout.** Root `bun install` replaces `package-lock.json`; scripts, `playwright.config.ts` webServer commands (`node e2e/fake-updater.mts`, `npx next dev`), portal Dockerfile and CI `check`/`e2e` jobs switch to Bun.
3. **Move to `apps/` + `packages/`.** `git mv` into the layout above, root `package.json` becomes the workspace root, single `bun.lock`, `@portail/shared` package, import rewrite, per-workspace tsconfig/vitest configs adjusted, root scripts.
4. **Dockerfiles and CI on the new layout.** Both images build from the repo root as context, install only their workspace (`bun install --filter`, frozen lockfile, production deps in the final stage), whitelist-style `.dockerignore` per image. CI jobs keep their current shape (check, updater, e2e, image, image-updater) and triggers, on Bun.
5. **Docs.** README development section, `.gitignore`, oxfmt ignore patterns updated.

## Verification (decided)

- **E2E runs against `bun --bun next dev`**, not the production build. Every spec authenticates through `x-dev-user-groups`, which `devUser()` only honours when `NODE_ENV === "development"`, and the standalone `server.js` forces `NODE_ENV = 'production'`. No test-only auth seam is added to application code.
- **Production smoke test** for the Bun-served standalone build (spike, and the built image): `/favicon.ico` → 200, `/auth-error` → 200, unauthenticated `/` → redirect to `/login`. Real sign-in and SSE streaming in production are only checked after deployment.
- **Work happens on a branch, merged once.** CI triggers stay as they are (e2e and image jobs only on `main`), so before merging the builder runs locally: `bun run e2e`, `docker build` of both images, then the smoke test against the portal container and `/health` on the updater container. Only one pair of `:latest` images is published, at merge. Steps 2–5 are separate commits on that branch, each passing lint/format/typecheck/test.

## Success criteria

- `bun install` at the root, then `bun run lint`, `bun run format:check`, `bun run typecheck`, `bun run test`, `bun run e2e` all pass.
- No `package-lock.json`, no `node` / `npx` / `npm` left in scripts, configs, Dockerfiles or CI (except a tolerated Node fallback inside Playwright's runner).
- Both images build and start: the portal container (`oven/bun`) passes the production smoke test on 3000, the updater answers `/health` on 8080.
- `git log --follow` works on moved files.

## Left to the builder

- Exact root script wiring (`bun run --filter '*' typecheck` vs explicit per-workspace calls).
- How `@portail/shared` is exposed (`exports` map pointing at `.ts` sources, no build step — both consumers bundle or run TS directly).
- Whether vitest runs per workspace or from one root config.
- Where `AGENTS.md` lives after the move.
- Dockerfile details beyond the constraints above.
