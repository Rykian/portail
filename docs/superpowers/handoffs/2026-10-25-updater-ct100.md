# Handoff : déployer et recetter l'updater sur CT 100

Pour : une session Claude Code qui tourne sur l'hôte Proxmox (ou directement dans CT 100), sans accès au repo ni à l'historique de la conversation qui a écrit l'updater. Tout ce qu'il faut est ici.

## Ce qu'est l'updater

Un service (NestJS sur Bun, image `ghcr.io/rykian/portail-updater:latest`) qui détecte et applique les mises à jour des stacks compose de CT 100. Il remplace WUD. Le portail (`ghcr.io/rykian/portail:latest`, https://payoux.net) en est la seule interface : page `/admin/updates`, réservée aux admins, qui parle à l'updater côté serveur sur un réseau Docker interne `updater`.

- L'updater monte `docker.sock` et `/root` : **accès équivalent à root**. Il n'est sur aucun autre réseau que `updater`, jamais sur `proxy`.
- Stacks découvertes automatiquement : chaque `/root/<dir>/` qui contient `compose.yml`, `compose.yaml`, `docker-compose.yml` ou `docker-compose.yaml`.
- Trois modes par stack : `pull` (tags flottants : pull + up + santé), `version` (réécrit une seule variable d'un `.env`), `recipe: authentik` (montée de version mineure d'Authentik avec le `compose.yml` amont).
- Après une mise à jour, l'updater vérifie la santé pendant 60 s maximum. En cas d'échec, pas de retour arrière automatique : un bouton « Revenir à … » apparaît.
- Comportements récents à connaître :
  - une stack **arrêtée** est seulement pullée et reste arrêtée ;
  - son retour arrière restaure fichiers et images sans la démarrer ;
  - une stack en `restarting` (crash loop) compte comme démarrée : elle est mise à jour, relancée et vérifiée ;
  - les conteneurs sont lus avec `docker compose ps` lancé depuis le dossier de la stack, donc un `name:` en tête du compose est respecté.

## Règles pour cette session

- **Demander à l'utilisateur avant** toute action difficile à annuler :
  - arrêter ou supprimer une stack (y compris WUD) ;
  - modifier un `compose.yml` ou un `.env` existant ;
  - lancer une sauvegarde vzdump. La rétention est `keep-last=1` : une nouvelle sauvegarde **remplace la seule existante**.
- Ne pas toucher `/root/authelia` (abandonné, mais on le laisse) ni les `*.back` / `*.bak-*`.
- Ne jamais afficher `UPDATER_TOKEN` ni les secrets `AUTH_*` dans tes réponses.
- Depuis l'hôte Proxmox, les commandes s'exécutent dans CT 100 : `pct enter 100`, ou `pct exec 100 -- bash -lc '<commande>'`. Tout tourne en root.

## 0. Prérequis (à vérifier avant tout)

1. Les images doivent être publiées. La CI ne pousse `portail` et `portail-updater` sur ghcr qu'après un push sur `main`. Si besoin, demande à l'utilisateur si le push est fait et si le job CI `image-updater` est vert, puis vérifie :
   ```bash
   docker pull ghcr.io/rykian/portail-updater:latest
   docker pull ghcr.io/rykian/portail:latest
   ```
   En cas de `denied` / `unauthorized`, les paquets ghcr sont privés : l'utilisateur doit faire `docker login ghcr.io` (token avec `read:packages`) ou rendre les paquets publics.
2. État de départ :
   ```bash
   docker version --format '{{.Server.Version}}'; docker compose version
   ls /root
   docker network ls | grep -E 'proxy|updater'
   ```
   Attendu : Docker 29, compose v5, réseau `proxy` présent, pas encore de réseau `updater`.

## 1. Déployer l'updater

```bash
mkdir -p /root/updater/data && cd /root/updater
printf 'UPDATER_TOKEN=%s\n' "$(openssl rand -hex 32)" > .env && chmod 600 .env
```

`/root/updater/compose.yml` :

```yaml
services:
  updater:
    image: ghcr.io/rykian/portail-updater:latest
    restart: unless-stopped
    env_file: .env
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
      - /root:/root # same path: compose resolves bind mounts on the client side
      - ./data:/data
    networks: [updater]

networks:
  updater:
    name: updater # normal bridge: needs outbound internet for registries
```

`/root/updater/config.yml` : c'est la config du design. **Vérifie chaque point avant de l'écrire** (voir après le bloc) :

```yaml
exclude: [authelia, updater, wud, "*.back", "*.bak-*"]

stacks:
  mealie:
    version: { file: .env, variable: VERSION }
  authentik:
    recipe: authentik
    version: { file: .env, variable: AUTHENTIK_TAG }
  sure:
    confirm: true
    before:
      - docker compose exec -T db pg_dump -U sure sure > backups/sure-$(date +%F).sql
  downloads:
    before:
      - tar czf backups/seer-$(date +%F).tgz seer
    beforeOnlyOnMajor: true
  frigate: { confirm: true }
  traefik: { last: true }
  cloudflared: { last: true }
  portal: { last: true }
```

Vérifications :
- `grep -n 'VERSION' /root/mealie/.env /root/mealie/*compose*.y*ml` : la variable existe dans le `.env`, et le compose l'utilise **avec accolades** (`${VERSION}` ou `${VERSION:-…}`). Un `$VERSION` sans accolades n'est pas reconnu. Même vérification pour `AUTHENTIK_TAG` dans `/root/authentik/`.
- `sure` : le service base s'appelle bien `db`, l'utilisateur et la base `sure` existent, `/root/sure/backups/` existe. Sinon, adapte la commande et dis-le à l'utilisateur.
- `downloads` : `/root/downloads/seer` et `/root/downloads/backups/` existent.
- Les commandes `before` tournent **dans le conteneur updater** (`sh`, `tar`, `gzip`, CLI Docker), dans le dossier de la stack, et pas sur l'hôte.
- Aucune stack n'a de `name:` en tête de compose qui la ferait entrer en collision avec une autre : `grep -l '^name:' /root/*/*compose*.y*ml`.

Démarrer :

```bash
cd /root/updater && docker compose up -d && docker compose logs --tail 50
docker network inspect updater --format '{{.Name}}'
```

## 2. Brancher le portail

Montre d'abord à l'utilisateur le diff de `/root/portal/compose.yml`, puis applique-le seulement après son accord. Cible :

```yaml
services:
  portal:
    image: ghcr.io/rykian/portail:latest
    restart: unless-stopped
    env_file: .env
    environment:
      SERVICES_FILE: /data/services.yml
      ICONS_DIR: /data/icons
      UPDATER_URL: http://updater:8080
    volumes:
      - ./data:/data:ro
    networks: [proxy, updater]

networks:
  proxy:
    external: true
  updater:
    external: true
```

Puis ajoute **le même** `UPDATER_TOKEN` au `.env` du portail (sans l'afficher) et relance le portail :

```bash
grep -q '^UPDATER_TOKEN=' /root/portal/.env || grep '^UPDATER_TOKEN=' /root/updater/.env >> /root/portal/.env
grep -c '^AUTH_URL=https://payoux.net' /root/portal/.env   # attendu : 1
cd /root/portal && docker compose pull && docker compose up -d
docker compose exec portal wget -qO- http://updater:8080/health
```

`AUTH_URL` est important. Le proxy `/api/updates/*` refuse tout POST dont l'en-tête `Origin` ne vaut pas l'origine de `AUTH_URL`. S'il manque, tous les boutons répondent 403. Et si les admins sur le LAN ouvrent le portail par une autre adresse que `https://payoux.net` (IP, nom local), leurs POST sont refusés : demande à l'utilisateur comment il y accède depuis le LAN.

## 3. Contrôles de l'API (dans CT 100)

```bash
cd /root/updater; set -a; . ./.env; set +a
IP=$(docker inspect -f '{{(index .NetworkSettings.Networks "updater").IPAddress}}' updater-updater-1)
curl -s http://$IP:8080/health
curl -s -X POST -H "Authorization: Bearer $UPDATER_TOKEN" http://$IP:8080/checks   # lance une vérification (job)
sleep 60; curl -s -H "Authorization: Bearer $UPDATER_TOKEN" http://$IP:8080/stacks | head -c 4000
```

Adapte le nom du conteneur si `docker ps` en affiche un autre. Une vérification interroge les registres pour chaque service : compte jusqu'à quelques minutes.

## 4. Recette (avec l'utilisateur, dans le navigateur sur https://payoux.net/admin/updates)

Coche chaque point et note ce que tu observes :

- [ ] Le menu avatar montre « Mises à jour » (avec le nombre s'il y en a) pour un admin, et rien pour un non-admin.
- [ ] La liste correspond aux stacks attendues : authentik, cloudflared, downloads, frigate, group-gate, ledfx, mealie, portal, sentinel-yt, stirling, sure, traefik. **Absentes** : authelia, wud, updater, `*.back`, `*.bak-*`. group-gate affiche « Passer la version dans une variable pour l'activer » (nginx figé en dur), sans bouton.
- [ ] Aucune stack en erreur inattendue. S'il y en a, relève le message exact.
- [ ] **stirling** : « Mettre à jour », suivre le journal en direct jusqu'à « réussie », puis « Revenir à … ». Ensuite, `docker inspect` du conteneur stirling montre l'ancien ID d'image (note-le avant la mise à jour : `docker compose -f /root/stirling/compose.yml images`).
  - S'il n'y a pas de mise à jour pour stirling, demande à l'utilisateur quelle autre stack sans base de données utiliser.
- [ ] **Mealie** (mode version) : mise à jour depuis la page, puis `diff` du `.env` (fais une copie avant) : seule la ligne `VERSION` change. Le conteneur tourne avec la nouvelle version.
- [ ] **Journal à travers Cloudflare** : pendant un pull long, le flux SSE ne coupe pas. S'il coupe, la page doit se reconnecter et rejouer le journal depuis le début sans doublon. Note toute coupure : il n'y a pas encore de heartbeat SSE (point M5 ci-dessous).
- [ ] **Historique** : les deux mises à jour et le retour arrière apparaissent avec utilisateur, versions et résultat, et un clic ouvre le journal.
- [ ] Pas de 403 sur les boutons, depuis Internet comme depuis le LAN.

Ne lance **pas** « Tout mettre à jour » ni Authentik, Sure ou Frigate sans l'accord explicite de l'utilisateur. Ces stacks migrent leur base, et le seul vrai filet est la vzdump.

## 5. Après la recette (seulement si tout est vert et avec l'accord de l'utilisateur)

Supprimer WUD : `cd /root/wud && docker compose down`, puis demander s'il faut supprimer `/root/wud` ou le renommer en `wud.bak-<date>`.

## Limites connues (ne pas corriger ici, juste signaler si elles se manifestent)

- **M2** : ajouter `confirm: true` dans la config n'a d'effet sur le bouton qu'après la vérification suivante.
- **M3** : quota Docker Hub anonyme (~10 pulls/h par IP). Une vérification manuelle suivie de « Tout mettre à jour » peut prendre un 429.
- **M5** : pas de heartbeat SSE. Un `before` long ou l'attente de santé de 60 s peut faire couper le flux par Cloudflare ou Traefik. La page se reconnecte, mais le journal clignote.
- **M8** : les journaux de plus de 90 jours sont purgés et s'affichent vides, sans explication.
- Le cron `docker system prune -f --volumes` de 04:30 ne touche pas les images de retour arrière (elles sont taguées `updater-rollback/<stack>-<service>:latest`).

## Ce qu'il faut rapporter à l'utilisateur

1. Ce qui a été déployé et modifié (fichiers, diffs du compose et du `.env` du portail, sans les secrets).
2. La checklist de la section 4, avec le résultat de chaque point.
3. Chaque anomalie avec : stack, action, message exact du journal ou de l'interface, sortie de `docker compose logs --tail 100` de l'updater.
4. Ce qui reste à décider (WUD, config `sure`/`downloads` adaptée, accès LAN).
